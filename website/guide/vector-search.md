# Vector search

Store embeddings next to your business data, index them, and search them from the repository: by meaning with `nearest()`, or by meaning and words together with `hybridSearch()`. No SQL specific to the database, and the usual filters (tenant, soft delete, criteria) apply before the ranking.

| Database | Vector type | Index | Full text |
| --- | --- | --- | --- |
| MariaDB 11.8+ | `VECTOR(n)` | HNSW (`VECTOR INDEX`) | `FULLTEXT` |
| PostgreSQL 15+ with pgvector 0.8+ | `vector(n)` | HNSW | GIN index on `to_tsvector()` |
| SQLite | text, distances computed in PHP | none: for tests and development | scored in PHP |
| MySQL | refused: Community has neither a vector distance nor a vector index | | |

::: warning Vectors do not work with MySQL
MySQL Community can store a `VECTOR` column, but it cannot compute a distance or index it: `DISTANCE()` is reserved for HeatWave and MySQL AI. Prism refuses a `vector` field on MySQL when the mapping is validated, so the error shows at startup, not in production. Use MariaDB 11.8+ or PostgreSQL with pgvector; the rest of Prism works on MySQL.
:::

Prism creates the `vector` extension of PostgreSQL with the schema, and refuses a pgvector older than 0.8.

The examples of this page are not run by the documentation tests, which also run on MySQL: the [demo application](https://github.com/prism-orm/demo) and Prism's functional tests run the same code on MariaDB, PostgreSQL and SQLite.

## A vector field

```php no-run
use Prism\Orm\Mapping as Prism;
use Prism\Orm\Vector\Distance;
use Prism\Orm\Vector\Vector;

#[Prism\Entity]
#[Prism\FullTextIndex(fields: ['title', 'content'], language: 'english')]
final class Article
{
    #[Prism\Id, Prism\GeneratedValue]
    public ?int $id = null;

    #[Prism\Column(length: 200)]
    public string $title;

    #[Prism\Column(type: 'text')]
    public string $content;

    #[Prism\Column(dimensions: 768)]
    #[Prism\VectorIndex(distance: Distance::Cosine)]
    public Vector $embedding;
}
```

- **The dimension is required.** It is the size of the column. A vector of another size throws `VectorDimensionMismatchException` before anything is sent to the database, with the class and the field.
- **A `Vector` is lazy.** A list of articles does not read 768 floats per row: Prism reads only whether the vector is `NULL`, and loads it on first access, for the whole batch at once. `->withVectors()` on a typed query reads them with the entities. A `list<float>` property (`#[Prism\Column(type: 'vector', dimensions: 768)] public array $embedding`) is always loaded.
- **`Vector` is a value object**: `toArray()`, `dimensions()`, `normalize()`, `cosine($other)`, `distance($other, Distance::Euclidean)`.

## Indexes

`#[VectorIndex]` builds an HNSW index on the field: `distance` is `Distance::Cosine` (default), `Distance::Euclidean` or `Distance::InnerProduct`; `m` (default 16) and `efConstruction` (default 64) tune the graph. The platform you target refuses what it cannot do, when the mapping is validated rather than at the first query:

- MariaDB indexes only `NOT NULL` vector columns, one vector index per table, and has no inner product.
- pgvector indexes up to 2,000 dimensions with HNSW.

On MariaDB, give the graph room: `mhnsw_max_cache_size` (16 MB by default) should hold the whole index, about 2 KB per vector of 768 dimensions. See [Measures](#measures).

`#[FullTextIndex]` is the index `hybridSearch()` searches, with the stemming of its `language` on PostgreSQL (`english`, `french`, `simple`…). Migrations create both: `createVectorIndex()` and `createFullTextIndex()` in a migration, generated by `db:migrations:diff`.

## nearest()

```php no-run
$articles = $em->getRepository(Article::class);

foreach ($articles->nearest('embedding', $question, limit: 5, criteria: ['published' => true]) as $hit) {
    echo $hit->entity->title, ' ', $hit->distance, ' ', $hit->score, "\n";
}
```

`nearest()` returns a `list<ScoredResult>` ordered from the closest: the entity, the `distance` the database computed (smaller is closer), and a `score` (larger is closer): `1 − d/2` for the cosine, `1/(1 + d)` for the euclidean distance. The distance is the one of the field's `#[VectorIndex]`, the cosine otherwise. The vectors are read with the entities.

The tenant filter, the soft-delete filter and the criteria apply **in the database, before the ranking**: a tenant never sees the nearest rows of another one. An HNSW index can return fewer rows than asked when a filter is selective. Prism guards against it on each platform: an iterative index scan on PostgreSQL (`hnsw.iterative_scan`), and on MariaDB an exact search when the index returned too few rows.

In a typed query, `distanceTo()` sorts or projects by distance:

```php no-run
$a = Article_::as('a');
$closest = $em->query($a)
    ->where($a->published->eq(true))
    ->orderBy($a->embedding->distanceTo($question)->asc())
    ->limit(5)
    ->getResult();
```

## hybridSearch()

A vector finds what means the same thing in other words; a full-text index finds the exact words, codes and names a vector blurs. `hybridSearch()` asks both and fuses the two rankings by **Reciprocal Rank Fusion**: each row scores `textWeight / (k + text rank) + vectorWeight / (k + vector rank)`.

```php no-run
use Prism\Orm\Vector\HybridOptions;

$hits = $articles->hybridSearch('partial payment', $question, limit: 10, criteria: ['published' => true]);
foreach ($hits as $hit) {
    echo $hit->entity->title, ' ', $hit->score, ' ', $hit->textRank ?? '-', ' ', $hit->vectorRank ?? '-', "\n";
}

// more weight to the words, 100 candidates from each list
$articles->hybridSearch('INV-2026-0042', $question, options: new HybridOptions(textWeight: 2.0, candidates: 100));
```

- The full-text part matches **any** of the words, on every platform, ranked by relevance.
- Each `HybridResult` exposes the fused `score` and both ranks, `null` when the row was not in that list.
- `HybridOptions`: `k` (60), `textWeight` and `vectorWeight` (1.0), `candidates` taken from each list (`max(4 × limit, 40)`), and `field` or `fullTextIndex` when the entity has several.

On the annotated questions of the demo, the hybrid search finds more relevant sections in its first ten results than the vector search alone; see [Measures](#measures).

## Keeping embeddings up to date

`#[EmbeddedVector]` computes the vector from text fields, and keeps it in step with them:

```php no-run
#[Prism\Column(dimensions: 768)]
#[Prism\VectorIndex(distance: Distance::Cosine)]
#[Prism\EmbeddedVector(source: ['title', 'content'], model: 'default')]
public ?Vector $embedding = null;
```

- Prism adds two columns, without properties: `embedding_stale` and `embedding_model`.
- **A new row is stale**, unless your code set the vector itself. **When a source field changes**, the flush marks the vector stale and leaves the old one in place.
- **A stale vector is left out of `nearest()`**, and of the vector half of `hybridSearch()`: it no longer matches its text. `nearest(..., includeStale: true)` and `new HybridOptions(includeStale: true)` keep it. A stale row is still found by its words.
- **After the commit**, never during the transaction, Prism hands the stale rows to a scheduler. With Messenger, it dispatches `ComputeEmbedding` messages, computed in batches by a worker, in the tenant of the rows. Without it, `db:embeddings:compute` computes them, and `db:embeddings:status` counts the stale ones. See [Embeddings in Symfony](/bundle/symfony#embeddings).
- **The computation** reads the texts, calls the provider outside any transaction, then writes each vector only if its texts did not change in the meantime. A concurrent edit is never overwritten with an old vector.

`model: 'default'` names an **embedding provider**. Prism makes no network call to an AI provider in its core: a provider implements `Prism\Orm\Vector\EmbeddingProvider` (`model()`, `dimensions()`, `embed($texts)`). The `prism-orm/embedding-openai` package speaks the `/v1/embeddings` API of OpenAI, Mistral, Ollama, vLLM, LocalAI and Text Embeddings Inference. `HashingEmbeddingProvider` is deterministic and offline, for tests: it brings together texts that share words, without understanding them.

To **change the embedding model**, change the provider, then mark every vector stale in a data migration; the worker or the command computes them again, and `embedding_model` tells which model computed each row:

```php no-run
public function run(EntityManagerInterface $em): void
{
    $em->getRepository(Article::class)->markEmbeddingsStale('embedding');
}
```

Without Symfony, give the entity manager a scheduler. The synchronous one computes the vectors right after the flush; share the filter collection, so that the computation sees the tenant filter:

```php no-run
use Prism\Orm\Filter\FilterCollection;
use Prism\Orm\Vector\EmbeddingProviderRegistry;
use Prism\Orm\Vector\EmbeddingUpdater;
use Prism\Orm\Vector\SynchronousEmbeddingScheduler;

$filters = new FilterCollection();
$providers = new EmbeddingProviderRegistry(['default' => $provider]);
$updater = new EmbeddingUpdater($connection, $metadata, $providers, $filters);
$em = new EntityManager($connection, $metadata, filters: $filters, embeddingScheduler: new SynchronousEmbeddingScheduler($updater));
```

## Measures

The demo searches the Prism documentation: 324 sections, `nomic-embed-text:v1.5` vectors (768 dimensions) on PostgreSQL, and 60 questions annotated by hand with the sections that answer them (112 in all). `bin/console app:docs:evaluate` ranks the sections for each question:

| Search | Recall@10 | MRR@10 |
| --- | --- | --- |
| `hybridSearch()` | **0.922** | 0.777 |
| vector only | 0.903 | **0.807** |
| full text only | 0.711 | 0.529 |

The hybrid search finds more of the relevant sections in its first ten results; the vector search alone more often puts the best one first. The corpus is small: these figures compare the three rankings with each other, they are not a public benchmark.

`make bench-vector` loads 100,000 random vectors of 768 dimensions into MariaDB and PostgreSQL, then times `nearest(limit: 10)`, entities hydrated:

| Database | `nearest()` p50 | p95 | Filtered to 1 % of the rows, p95 |
| --- | --- | --- | --- |
| MariaDB 11.8.6 | 21 ms | **22 ms** | 410 ms |
| PostgreSQL 16, pgvector 0.8.7 | 27 ms | **31 ms** | 29 ms |

Measured on 2026-10-28: Intel Xeon Gold 5218, 8 cores, 7.7 GB of RAM shared with the other services, the databases in Docker; HNSW with `m = 16`, cosine distance; 200 searches to warm up, 200 measured, each with a new vector. The script is `tools/bench/vector-nearest.php`.

- **Size the HNSW cache of MariaDB.** MariaDB keeps the graph in `mhnsw_max_cache_size`, 16 MB by default: far too little for 100,000 vectors of 768 dimensions, whose graph is then read again on each search. The benchmark sets it to 1 GB; with the default, the same search takes 65 ms at p95 and the index takes 23 minutes to build instead of 3.
- **A selective filter costs more on MariaDB.** When a filter keeps few rows, the HNSW index of MariaDB returns too few of them, and Prism falls back to an exact search over the rows the filter keeps, through the index of the filtered column. Its cost grows with those rows and with the InnoDB buffer pool (128 MB here). PostgreSQL scans its index iteratively until it has enough rows. Index the column you filter on, as Prism does for `tenant_id`. The migration linter warns (L21) when a vector index is created on a tenanted table of MariaDB where one tenant, among others, has more than 10,000 rows.
